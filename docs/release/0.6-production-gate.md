# Notare 0.6 — Production Gate

The checklist that gates a 0.6 **production** release. Same policy as 0.5
(QA/release-gate, 2026-07-22): an RC may ship with *documented* known edge cases;
**production may not ship with any open `GATE: BLOCK` row.** Every row needs
evidence per platform (Linux verified on coruscant; macOS/Windows gated on
Abhishek). RC path: `0.6.0-rc.n` (edge cases allowed) → production (none).

Legend: ✅ pass (evidence) · ⚠️ RC-acceptable known edge case · ⛔ BLOCK (must clear
before production) · ▫️ not yet exercised on this platform.

## 0. What 0.6 is — and the re-scope that produced it

**0.6 was scoped as the P2P sync release. Sync is deferred to 0.7.** The ELv2
determination that cleared sqlite-sync as the CRDT engine was withdrawn on
2026-09-02 (`docs/LICENSE-NOTE.md`); SQLite Cloud's written reply denies use of the
custom network layer the whole transport is built on. The sync gate rows are carried
forward intact in **`docs/release/0.7-sync-gate.md`** — no evidence was discarded.

**Deferring cost no code.** `release.yaml:68,126` build `--features
gpu-vulkan,directml` and `gpu-vulkan`; `sync` is in neither and never was. The sync
stack has never reached a user.

### What that leaves — stated plainly

Removing sync leaves less than it looks. Measured against `v0.5.2`, `main` carried
115 non-merge commits at the time of the re-scope, of which ~75 were sync and 14
non-sync — and of those 14, exactly one was user-facing: the trash view
(`226ad741d`, contained in zero tags).

That inventory is what made the version question live. It was answered by bringing
the local LLM into release builds (see the decision below), which is new content
rather than a reinterpretation of existing content.

Everything else people sometimes associate with this cycle already shipped —
verified with `git tag --contains`:

| Feature | First shipped in |
|---|---|
| On-device diarization + voice recognition | **v0.4.0** |
| Hybrid search tab | **v0.5.0** |
| Action-items checklist UI | **v0.5.0** |
| Recording finalize-on-exit / orphan recovery / rename-hang (#101, #102, #105) | **v0.5.0** |

### Decided 2026-09-03: 0.6 is a minor version, and the local LLM is its headline

The version question above was live when this page was first written. It is
settled: **the embedded local LLM ships** (§D), and that is enough to carry a
minor version on its own — an on-device chat/summarisation model is a larger
change than everything else in this release combined.

### Row 4 — the models are NOT mirrorable from Hugging Face

All three GGUFs download from `hyprnote.s3.us-east-1.amazonaws.com` — **Fastrepl's**
bucket, not ours (`crates/local-model/src/lib.rs`). Live as of 2026-09-02, but
Fastrepl has moved to a separate closed product, so this is an availability
dependency on a third party for a now-shipping feature.

The obvious fix — repoint to Hugging Face with pinned revisions, matching what
`parakeet-onnx-model` and `voxtral-llama-model` already do — **was attempted in
#162 and reverted.** All three HF files return *exactly* the recorded
`model_size()`, which looks like a clean drop-in. It is not:

| copy | sha256 | crc32 |
|---|---|---|
| **S3** (current) | `d772bf66…` ✅ matches recorded | `4037351144` ✅ matches recorded |
| **HF** `yujonglee/hypr-llm-sm` | `bda23bd1…` ✗ | `378658602` ✗ |

Same byte count, genuinely different files — established by downloading both 1.1GB
copies and hashing them, not by trusting `Content-Length` or the LFS etag (the HF
repo is Xet-backed, so its etag is not a plain sha256 and reads as a false mismatch
on its own). Repointing would have failed **both** download gates for every user.

**So closing this row means mirroring the S3 bytes to storage we control**, not
repointing to HF. Until then it stays ⛔, and the risk is: if that bucket goes
away, the local LLM breaks for every new install (existing installs keep their
downloaded weight).

Model **integrity** is handled — CRC32 + SHA-256 per model, consistent with
ADR-0002. It is **availability** that is unguarded.

## Summary — what blocks 0.6 production today

1. ⛔ **One macOS session and one Windows session** (§A, §D2.2) — clears most of the
   carried 0.5 table *and* the "local LLM has never been executed off Linux" row.
   No precondition; signed macOS builds already ship (§B).
2. ⛔ **Model availability** (§D2.4) — mirror the S3 weights to storage we control.
   Hugging Face is **not** a drop-in substitute; that was tried and reverted.
3. ⛔ **OS-wise regression report** (§A) — never started.
4. ⛔ **`main` has no required status checks** (§F) — repo setting.
5. ⚠️ **Measure the release build cost** (§D2.3) — first tagged build after #162.
6. ⚠️ **`server.rs` generation-path coverage** (§D2.1) — the contract is tested; the
   SSE path still needs a trait over `generate`.

Rows 1, 3 and 4 are gated on Abhishek: hardware and a repo setting. Row 2 is real
work. Rows 5–6 are follow-ups that an RC may carry.

**Settled, no longer blockers:** the version question (§0 — it is a minor, with the
local LLM as headline), the `local-llm` shipping decision (§D2 — it ships, #162),
and #19 macOS signing (§B — done and shipping since v0.5.0). Earlier drafts of this
page listed all three as open.

**#19 (macOS signing) is NOT on this list** — it is done and shipping (§B). An
earlier draft had it as blocker #1 and as the ordering constraint for row 1; that
was read off a stale workflow comment rather than the repo, and is corrected.
