# Notare 0.7 — P2P Sync Gate

Sync was 0.6's headline. It is **deferred to 0.7**, for a reason that is not a code
defect: the ELv2 determination that cleared sqlite-sync as the CRDT engine was
withdrawn on 2026-09-02 (`docs/LICENSE-NOTE.md`). This file carries the sync gate
rows forward so none of the evidence built during the 0.6 cycle is lost.

**Engine decided (2026-09-07, Abhishek): swap to cr-sqlite (vlcn-io, MIT), pinned
at v0.16.3.** The §0 blocker is closed. What follows is re-scoped against that
engine. The per-table id-provenance analysis (§25–§29 of `sync-p2p.md`, ported
to main by this change) carries to the new engine because it is about
application id minting, not merge semantics; its dated corrections — the §25.3
organizations finding, the §26.3 disconnect hazard, the §27.4 seeder fix — are
marked inline.

**Deferring cost nothing to ship.** `release.yaml` builds with
`--features gpu-vulkan,directml,local-llm` / `gpu-vulkan,local-llm-vulkan` /
`local-llm` per platform; `sync` is in none of them, and never was. The
stack is additionally gated by the `sync` cargo feature (default-off), the
`sync_platform` cfg (`build-support/sync_app_gate.rs`), and the `sync_enabled`
runtime setting (default-off, read at `apps/desktop/src-tauri/src/lib.rs:437`). No
build output changes as a result of this deferral.

### If the engine swaps — what carries and what does not (2026-09-02 scoping; now the plan of record)

A contingency scoping pass against cr-sqlite (vlcn-io, MIT) found:

- **Carries:** the iroh/QUIC transport, device identity (`identity.rs`), the peer
  allowlist (`peers.rs`), XChaCha20-Poly1305/X25519 E2E (`crypto.rs`), the pairing
  UI, and the eight `sync_*` specta commands. `cargo test -p sync-p2p` passes 28
  tests with **no sqlite-sync extension present**, which is that split demonstrated
  rather than argued. (2 of the 28 test the collapsed-S3 broker, which does not
  carry.)
- **Does not carry:** `crates/cloudsync` entire (~1,900 LOC + a 28 MB vendored C
  tree), `sync-p2p/src/broker.rs` (the S3-shaped control plane), the drain loop and
  `MAX_DRAIN`, the C↔agent localhost socket and its bearer token, the
  `max_connections(1)` clamp, and the `from-source` build with its CI jobs.
- **Compatibility, checked against `core/rs/core/src/tableinfo.rs::is_table_compatible`:**
  the synced tables clear cr-sqlite's gate on paper — TEXT non-null PKs, no
  unique index beyond the PK, no AUTOINCREMENT, no declared foreign keys, and NOT
  NULL columns already carry DEFAULTs (cr-sqlite enforces the *same* DEFAULT rule
  sqlite-sync does, so it is already satisfied).
- **The one unverified gap: `STRICT` tables.** 18 of notare's tables are `STRICT`.
  cr-sqlite stores changeset values dynamically-typed and writes them back through
  the base table; if a type does not round-trip exactly, `STRICT` rejects the apply.
  Nothing upstream documents this and no test covers it. **Phase 0 spike
  (`chore/crsqlite-strict-spike`) gates everything** — two in-process DBs, no
  transport, one sitting.
- **Upstream state re-verified 2026-09-07:** `vlcn-io/cr-sqlite` latest release
  **v0.16.3**, latest commits Aug 2026 (build packaging only: macOS headerpad,
  Windows arm64 loadable, Android); prebuilt loadable-extension binaries for
  Linux/macOS/Windows are attached to releases. **This is the engine to pin.**
  `superfly/cr-sqlite` stays at `v0.18.0-v2-migration-alpha9` (Aug 2024), needs
  nightly Rust, changes the `crsql_changes` schema — a future option only, noted
  because its per-peer `(db_version, seq)` cursor shape is where its migration
  path heads anyway.

## A. Per-table gates

`SYNCED_TABLES` is **6 of 17** registered tables. The 8-of-17 figure this table
carried before was written against the `feat/sync-table-proofs-b1` branch, not
main — main never enabled the batch 2–4 tables. Every enabled table has a
§17-style convergence proof against its **real** schema and the app's **real**
write SQL, run against sqlite-sync 1.0.12 (historical; see the engine banner in
`docs/internal/sync-p2p.md` above §25). Those proofs are evidence about `cls`
merge semantics and **must be re-proven under cr-sqlite** before 0.7 ships; every
row is therefore ▫️ until the `crates/sync-p2p/tests/table_proofs/` harness
(0.7 plan C-F/B6) lands it.

| Table | Status | Evidence |
|---|---|---|
| `sessions` | ▫️ re-prove under cr-sqlite | §17 (SYNC-6 part A) against sqlite-sync — real schema, TEXT-PK, STRICT, tombstones, no resurrect |
| `session_documents` | ▫️ re-prove under cr-sqlite | §17 + the §19 FK correction, against sqlite-sync |

⚠️ **Proofs do not run in CI — the 0.7 shape fixes that.** Today nothing in
`.github/workflows/` runs the proof examples; all hand-run evidence is
linux/x86_64. The 0.7 plan replaces the hand-run examples with the
`crates/sync-p2p/tests/table_proofs/` convergence tests (one file per batch,
named assertions: `converge`, `concurrent_columns`, `tombstone_no_resurrect`,
`readd_after_tombstone`, `alter_replay`, `large_row`, `identity_dedup`,
`strict_roundtrip`) wired into a `sync_table_proofs_linux` CI job, promoted into
`ci.needs` after the usual green-on-several-PRs bar. Batches 2–4 GO verdicts
from the retired harness are re-run there, not inherited; NO-GO verdicts carry
as reasoning (the NO-GO table below, in this section).

### Tables deliberately NOT enabled

Four are **proven unsafe**, not merely unproven — each duplicates the entity under
concurrent creation because the primary key is a locally-minted
`crypto.randomUUID()` while the real identity lives elsewhere. **This analysis
is about application id minting, not the engine — it survives the swap to
cr-sqlite unchanged.** The `db-app` guard test
`cloudsync_registry_enables_only_the_proven_tables`
(`crates/db-app/src/lib.rs:580`) pins the enabled set (6 tables) and asserts
only that `calendars` is not enabled; the **full four-verdict pin — NO-GO
assertions for `humans`, `session_participants`, `events` alongside the
existing one, plus `ELIGIBLE_PENDING_PROOF` for the four branch-verdict
tables and disjointness assertions** — lands in `chore/pin-sync-no-go-verdicts`
(plan B2).

| Table | Status | Real identity | Evidence | Fix |
|---|---|---|---|---|
| `humans` | ⛔ do not enable | `lower(email)` | §25.2 — duplicates on both write paths | deterministic id + backfill (plan B4) |
| `session_participants` | ⛔ do not enable | `(session_id, human_id)` | §25.2 | deterministic id + backfill (plan B4) |
| `calendars` | ⛔ do not enable | `tracking_id_calendar` | §26.2 | deterministic id (plan B5); **also gated by the §26.3 disconnect hazard — stays disabled in 0.7 even after the id fix** |
| `events` | ⛔ do not enable | `tracking_id_event` | §26.2 — worst case: the duplicating write is the poller, so it fires per device automatically | deterministic id (plan B5); **same §26.3 hazard** |

One GO from the branch carries a **caveat that downgrades it**: `organizations`
was GO on the branch (§25.3), but the branch's premise — "no find-or-create-by-
name path" — is false (`updateHuman` with `companyName`,
`apps/desktop/src/contacts/queries.ts:548-560`, mints `id()` behind a
`NOT EXISTS lower(name)` guard; the same §25.2 defect class). It moves to
**eligible pending fix**: needs deterministic ids (plan B4) and the cr-sqlite
re-proof before enabling. See the §25.3 correction in `sync-p2p.md`.

Four are **eligible, pending fix + re-proof** — GO-verdict tables from the
branch that stay disabled on main until both the named fix and the cr-sqlite
re-proof land: `organizations` (B4), `templates` (B3 + T-5), `chat_groups` and
`chat_messages` (§29.1; the §29.3 regenerate caveat is a chat-feature follow-up,
not a sync blocker).

Three are **unused** — no live app write path, so there is no write pattern to
model: `daily_notes` and `session_attachments` (only `legacy_import.rs`),
`entity_mentions` (nothing, anywhere). §28.

The `cloudsync` from-source row is gone: the from-source build and its CI jobs
are deleted with the engine (plan C-C/C-G). The "three-node convergence over a
static hub" row is re-named — the 0.7 protocol v2 replaces the elected hub with
a pull-only full mesh, and the three-node proof becomes "A↔B and B↔C only, C
converges without contacting A".

⛔ **GATE: BLOCK — executed off Linux.** Nothing has ever *run* the sync stack
off linux/x86_64. With cr-sqlite there is no custom C network layer, so the
Winsock2-vs-POSIX risk is gone — but "compiled" is still not "executed", and
the packaged dylib/so/dll has never been loaded by a signed app on macOS or
Windows. Clearing this needs `cargo test -p crsqlite` plus the convergence
tests actually running on the macOS/Windows CI runners (plan C-B/C-F), and the
macOS Gatekeeper-on-unsigned-dylib question settled there (`crsqlite_gate_macos`
is the first execution; packaging 1b static removes it).

⛔ **GATE: BLOCK — packaged-install verification.** #154 fixed two defects that
made installed builds unlaunchable (the from-source extension resolved a
compile-time `OUT_DIR` path that does not exist on a user's machine; and a
failed extension load panicked before tracing existed, killing the process
silently). The fix is compile-proven and regression-tested, and a
`desktop_test_build` ran green — but that proves the build, not the install.
cr-sqlite keeps the shape of this risk: it is still a loadable extension
resolved at app start. The 0.7 packaging (vendored prebuilt binaries extracted
to the cache dir, `bundle.rs`-style, no `OUT_DIR` path) is designed against
exactly the #154 class, but a packaged install still has to be verified on all
three OSes.

### Correction carried forward — RESOLVED

The old correction observed that `plugins/db/src/sync.rs:21` describes an
"elected-hub topology" while no election exists in the code. **Resolved by the
engine swap and the 0.7 topology statement:** protocol v2 is a pull-only
symmetric full mesh over the allowlist — no hub, no broker, no election; every
paired device is a peer, one version cursor per peer (`sync_peer_cursors`),
changes carry their origin `site_id` so a relayed change applies once and is
attributed correctly. The self-pointing `connection_string` was a broker
artefact and is removed with it (plan C-C). The three-node proof wires A↔B and
B↔C only and asserts C converges with A without contacting it.

## D. Non-goals carried from 0.6 (re-scoped for cr-sqlite)

Recorded so they read as decisions rather than omissions. The hub/broker/`strstr`
items are struck: they were sqlite-sync-architecture artefacts and are deleted
with the engine.

- ~~**Hub failover / election**~~ — removed with the broker; the 0.7 topology is
  a pull-only full mesh with no hub to fail over (§B's correction, resolved).
- ~~**Blob-log GC**~~ — removed with the broker; cr-sqlite has no blob log.
  (`session_attachments`' separate file-sync design problem remains if that
  feature is ever revived — §28.)
- **The 11 disabled tables** — 4 proven unsafe (fix named in §25.4/§26.3, plans
  B4/B5), 4 eligible pending fix + re-proof (§25.3 correction, §27.4, §29.1),
  3 unused (§28). None is enabled merely for want of a proof.
- ~~**`strstr`-based JSON parsing** in `network_p2p.c`~~ — deleted with the C
  network layer; protocol v2 is a typed `SyncMessage` enum over an encrypted
  length-prefixed frame.
- **No hostile-broker/peer test fixture** (§12) — still open; with the broker
  gone this narrows to "behaviour against a malicious or malformed *peer*",
  which the allowlist checks in `accept_iroh` partly cover.
- **Scheduled re-run of the `#[ignore]`d real-network discovery test** (§20.10).
- **`templates` fresh-device re-seed** (§27.4) — fix is plan B3: seed-marker
  migration **plus** a `templates.deleted_at` tombstone, because the seed is
  re-run by `repair_missing_core_tables`, so a marker alone cannot know a fresh
  device will join a sync set. Whether the tombstone out-versions the fresh
  insert under cr-sqlite LWW is **proof row T-5**; fallback: seed lazily in the
  app after first sync.
- **Chat regenerate caveat** (§29.3) — `deleteChatMessagesExcept` prunes by
  `NOT IN` over a local snapshot, so a concurrent append survives a regenerate
  with an incoherent transcript. App-logic defect, carries to any engine; fix
  is a chat-feature change (branch/parent ids), recorded as a follow-up.
- **`calendars`/`events` deliberately not synced in 0.7** (§26.3) — beyond the
  id problem, they carry per-device connection state (`calendars.enabled`, the
  poller's disconnect tombstone sweep), so a disconnect on one device would
  tombstone events everywhere. Deterministic ids land (B5) to fix
  `sessions.event_id` portability; the enable decision is deferred beyond 0.7.

## Summary — what blocks 0.7 sync today

1. ✅ ~~Engine undetermined~~ — **resolved** (§0): cr-sqlite v0.16.3, MIT.
   Prerequisite: the Phase 0 STRICT spike (`chore/crsqlite-strict-spike`) and
   the `table_proofs` harness land and pass.
2. ⛔ The sync stack has never been executed on macOS or Windows (§B) — clears
   when `crsqlite_gate_*` and the convergence tests run on those CI runners.
3. ⛔ No packaged install verified (§B) — re-scoped: the cr-sqlite packaging
   (vendored prebuilt binaries, no `OUT_DIR` path) is designed against the #154
   class, but no install has been verified on any OS against the new engine.
4. ⚠️ Per-table proofs are hand-run and outside CI (§A) — every enabled table
   is ▫️ until its `table_proofs` batch lands in CI.

Order still matters: the STRICT spike gates everything, then the harness, then
per-table re-proofs in CI, then off-linux execution, then the packaged install.
The §A re-proofs are evidence about cr-sqlite's merge semantics, and the old
sqlite-sync proofs do not substitute for them — the id-provenance analysis
(§25–§29) does carry, unchanged.
