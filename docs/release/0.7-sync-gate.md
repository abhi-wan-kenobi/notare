# Notare 0.7 — P2P Sync Gate

Sync was 0.6's headline. It is **deferred to 0.7**, for a reason that is not a code
defect: the ELv2 determination that cleared sqlite-sync as the CRDT engine was
withdrawn on 2026-09-02 (`docs/LICENSE-NOTE.md`). This file carries the sync gate
rows forward so none of the evidence built during the 0.6 cycle is lost.

**Deferring cost nothing to ship (0.6.0–0.6.7).** Through 0.6.7, `release.yaml`
never passed `--features sync`. The stack is additionally gated by the `sync` cargo
feature (default-off), the `sync_platform` cfg (`build-support/sync_app_gate.rs`),
and the `sync_enabled` runtime setting (default-off, read by `sync_enabled_setting`
in `apps/desktop/src-tauri/src/lib.rs`).

## Status — 2026-11-04: shipping as a preview in 0.6.8

Decision: 0.6.8 compiles sync into all three release builds as a **preview**,
off by default. This does not clear the 0.7 gate. §B's two BLOCK rows still stand
for calling sync done.

- **Build:** the three `tauri build` lines in `.github/workflows/release.yaml`
  (windows-latest x86_64, ubuntu-24.04 x86_64, macos-latest aarch64) add `sync`
  to `--features`. All three targets are inside the `sync_platform` gate. Dev
  builds without the flag are unchanged.
- **Off by default:** `sync_enabled` still defaults to `false`; at startup the
  agent is not started unless it is `true`. Settings → Devices carries a
  "Preview" badge, and the sidebar label reads "Devices (preview)".
- **First-run safety:** `start_sync` runs `crsql_as_crr` on the six
  `SYNCED_TABLES` (`plugins/db/src/sync.rs` `SyncLifecycle::prepare`). The
  Settings toggle now detects whether any `*__crsql_clock` table exists. If none
  does, it asks "This changes how Notare stores notes so they can sync. Back up
  first?" ([Open data folder] [Continue]). Nothing is persisted or converted
  until the user clicks Continue. The engine itself still loads at startup, but
  loading it converts no table.
- **Startup panic fixed before shipping:** with the engine loaded, the first
  packaged smoke run logged 4 `sqlx-sqlite-worker` panics ("unable to close due
  to unfinalized statements"). Cause: `hypr_tauri_utils::block_on` (db and
  embedding-search plugin setup) ran on a throwaway runtime, so the tasks sqlx
  spawns to return a connection to the pool were cancelled when that runtime was
  dropped. Each connection then closed without `crsql_finalize`. `block_on` now
  runs on the caller's multi-thread runtime. Regression test:
  `crates/tauri-utils` `tasks_spawned_inside_outlive_the_call`. 0.6.7 could not
  hit this because it never loaded the engine.
- **Packaged smoke (Linux x86_64, ✅ 2026-11-04):** `scripts/sync-packaged-smoke.sh`
  builds `cargo build -p desktop --release --features sync`, launches it under
  Xvfb with a fresh HOME, and asserts `show_main_window`, 0 `panicked`, 0
  `Unrecoverable render error`, the db plugin's `cr-sqlite sync engine loaded
  (v0.16.3): …/.cache/notare/crsqlite/0.16.3/linux-x86_64/crsqlite.so` line
  (emitted after a `crsql_site_id()` probe), sync left off, and no CRR table in
  the fresh `app.db`. All checks passed.
- **Unverified:** macOS (Gatekeeper / notarization, i.e. whether a signed app may
  `dlopen` the cr-sqlite dylib it extracts to `~/Library/Caches`) and Windows
  (loading the extracted DLL) are unverified until someone runs 0.6.8 there. If
  loading fails, `db::open_desktop_db` reopens the database without the engine, the
  app runs as a local notes app, and Settings → Devices reports "Sync engine not
  loaded on this build".

Legend: ✅ pass (evidence) · ⚠️ known edge case · ⛔ BLOCK · ▫️ not yet exercised.

## 0. The blocking question — which engine

✅ **GATE: RESOLVED — swapped to cr-sqlite (MIT).** See `docs/LICENSE-NOTE.md`.

| Item | Status |
|---|---|
| SQLite Cloud replied denying use of a custom network layer (2026-09-02) | recorded |
| Decision: swap to cr-sqlite (vlcn-io v0.16.3, MIT) + Protocol v2 | ✅ **done in 0.6.6** |
| Remove legacy `crates/cloudsync`, C network layer, and `from-source` CI | ✅ **done in 0.6.7** |

Everything below §0 was originally written during the 0.6 cycle under sqlite-sync and is updated here to reflect the active **cr-sqlite (vlcn-io v0.16.3)** engine and **Protocol v2** (`crates/sync-p2p`).

### What carried and what was removed in the engine swap

The engine swap to cr-sqlite (decided 2026-09-07, implemented in 0.6.6 / 0.6.7) settled the architectural boundary:

- **Carried:** the iroh/QUIC transport, device identity (`identity.rs`), the peer
  allowlist (`peers.rs`), XChaCha20-Poly1305/X25519 E2E (`crypto.rs`), the pairing
  UI, and the eight `sync_*` specta commands.
- **Does not carry (removed in 0.6.7):** `crates/cloudsync` entire (~1,900 LOC + a 28 MB vendored C
  tree), `sync-p2p/src/broker.rs` (the S3-shaped control plane), the drain loop and
  `MAX_DRAIN`, the C↔agent localhost socket and its bearer token, the
  `max_connections(1)` clamp, and the `from-source` build with its four CI jobs.
- **Compatibility, checked against `crates/crsqlite/tests/strict_roundtrip.rs`:**
  the synced tables clear cr-sqlite's gate — TEXT non-null PKs, no unique index
  beyond the PK, no AUTOINCREMENT, no declared foreign keys, and NOT NULL columns
  already carry DEFAULTs.
- **STRICT tables (probed and verified):** 18 of notare's tables are `STRICT`.
  The Phase 0 spike (`crates/crsqlite/tests/strict_roundtrip.rs`, `sync-p2p.md §30`)
  proved byte-exact value and typeof equality for all SQLite storage classes across
  the pull→codec→apply path. TEXT PKs require explicit `NOT NULL`.
- **Maintenance risk & packaging:** upstream cr-sqlite's pinned release is `v0.16.3`
  (vlcn-io, MIT). Prebuilt binaries are embedded in `crates/crsqlite/vendor/` across
  the four supported targets and extracted at runtime via `bundled_extension_path()`,
  avoiding dynamic build-time compilation.

(`crsqlite_gate_{linux,macos,windows}`) across supported platforms, but automated
two-node schema convergence tests for all synced tables belong in 0.7's CI scope.
### Tables deliberately NOT enabled

Four are **proven unsafe**, not merely unproven — each duplicates the entity under
concurrent creation because the primary key is a locally-minted
`crypto.randomUUID()` while the real identity lives elsewhere. The `db-app` guard
test pins all four verdicts. **This analysis is about application id minting, not
the engine — it survives an engine swap unchanged.**

| Table | Status | Real identity | Evidence |
|---|---|---|---|
| `humans` | ⛔ do not enable | `lower(email)` | §25.2 — duplicates on both write paths |
| `session_participants` | ⛔ do not enable | `(session_id, human_id)` | §25.2 |
| `calendars` | ⛔ do not enable | `tracking_id_calendar` | §26.2 |
| `events` | ⛔ do not enable | `tracking_id_event` | §26.2 — worst case: the duplicating write is the poller, so it fires per device automatically |

Three are **unused** — no live app write path, so there is no write pattern to
model: `daily_notes` and `session_attachments` (only `legacy_import.rs`),
`entity_mentions` (nothing, anywhere). §28.

Two remain **unproven and unattempted**: `chat_groups`, `chat_messages`. §25.1.
(`feat/sync-table-proofs-b1` / PR #157 carries proofs for these plus batch 3–4
enables; **parked** pending §0.)

⛔ **GATE: BLOCK.** Nothing has ever *run* the full desktop sync stack off linux/x86_64.
cr-sqlite eliminates the custom C socket layer (`network_p2p.c`) and Winsock2-vs-POSIX
risk entirely. However, a live two-peer P2P round trip between real desktop installations
has been verified primarily on Linux; clearing this gate requires verification on physical
or VM macOS and Windows installations.

⛔ **GATE: BLOCK — packaged-install verification.** #154 fixed two defects that made
installed builds unlaunchable (resolving a compile-time `OUT_DIR` path that does not
exist on a user's machine, and unhandled early extension load errors). Under cr-sqlite,
binaries are bundled via `include_bytes!` and extracted to `dirs::cache_dir()`, which
eliminates the `OUT_DIR` failure class. Packaged installer launch must still be verified
on real installations before 0.7 release.

### Correction carried forward

The legacy S3-shaped localhost broker and elected-hub topology from early 0.6 spikes
were completely removed in 0.6.7. Protocol v2 sessions are direct peer-to-peer over
iroh QUIC bi-streams (`crates/sync-p2p/src/session.rs`).

## D. Non-goals carried from 0.6

Recorded so they read as decisions rather than omissions.

- **Hub failover / election** (§15.2, §20.10) — unbuilt. Note the app does not
  implement election at all today; see §B's correction.
- **Blob-log GC** (§15.2, §20.10) — moot: cr-sqlite has no blob log, and the legacy broker was deleted in 0.6.7.
- **The 9 remaining disabled tables** — 4 proven unsafe (fix named in §25.4/§26.3),
  3 unused, 2 unproven.
- **`strstr`-based JSON parsing** in `network_p2p.c` (§12, §21.4) — moot: the custom C network layer was deleted in 0.6.7.
  malicious or malformed peer.
- **Scheduled re-run of the `#[ignore]`d real-network discovery test** (§20.10).
- **`templates` fresh-device re-seed** (§27.4) — a device joining an existing sync
  set replays the default-template seed and resurrects built-ins deleted elsewhere.
  Nodes converge, so it is a seeder bug, not a CRDT one — but enabling `templates`
  is what makes it cross-device. Fix belongs in the seeder (seed once per database
  behind a marker). A reviewer may reasonably reverse the decision to enable
  `templates` because of this.

## Summary — what blocks 0.7 sync today

1. ✅ **Engine settled** (§0) — swapped to cr-sqlite (MIT) in 0.6.6; `crates/cloudsync` removed in 0.6.7.
2. ⛔ The full sync stack has never been executed on macOS or Windows (§B).
3. ⛔ Packaged install verified on all target platforms since cr-sqlite packaging (§B).
4. ⚠️ Automated convergence proofs in CI across supported platforms (§A).

Order matters: **address 2, 3 and 4 before release.**
