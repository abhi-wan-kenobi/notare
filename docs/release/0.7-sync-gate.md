# Notare 0.7 — P2P Sync Gate

Sync was 0.6's headline. It is **deferred to 0.7**, for a reason that is not a code
defect: the ELv2 determination that cleared sqlite-sync as the CRDT engine was
withdrawn on 2026-09-02 (`docs/LICENSE-NOTE.md`). This file carries the sync gate
rows forward so none of the evidence built during the 0.6 cycle is lost.

**Deferring cost nothing to ship.** `release.yaml:68,126` build `--features
gpu-vulkan,directml` and `gpu-vulkan`; `sync` is in neither, and never was. The
stack is additionally gated by the `sync` cargo feature (default-off), the
`sync_platform` cfg (`build-support/sync_app_gate.rs`), and the `sync_enabled`
runtime setting (default-off, read at `apps/desktop/src-tauri/src/lib.rs:437`). No
build output changes as a result of this deferral.

Legend: ✅ pass (evidence) · ⚠️ known edge case · ⛔ BLOCK · ▫️ not yet exercised.

### If the engine swaps — what carries and what does not

A contingency scoping pass against cr-sqlite (vlcn-io, MIT) found:

- **Carries:** the iroh/QUIC transport, device identity (`identity.rs`), the peer
  allowlist (`peers.rs`), XChaCha20-Poly1305/X25519 E2E (`crypto.rs`), the pairing
  UI, and the eight `sync_*` specta commands. `cargo test -p sync-p2p` passes 28
  tests with **no sqlite-sync extension present**, which is that split demonstrated
  rather than argued. (2 of the 28 test the collapsed-S3 broker, which does not
  carry.)
- **Does not carry:** `crates/cloudsync` entire (~1,900 LOC + a 28 MB vendored C
  tree), `sync-p2p/src/broker.rs` (the S3-shaped control plane), the drain loop and
  `MAX_DRAIN`, the C↔agent localhost socket and its bearer token, the
  `max_connections(1)` clamp, and the `from-source` build with its four CI jobs.
- **Compatibility, checked against `core/rs/core/src/tableinfo.rs::is_table_compatible`:**
  the eight enabled tables clear cr-sqlite's gate on paper — TEXT non-null PKs, no
  unique index beyond the PK, no AUTOINCREMENT, no declared foreign keys, and NOT
  NULL columns already carry DEFAULTs (cr-sqlite enforces the *same* DEFAULT rule
  sqlite-sync does, so it is already satisfied).
- **The one unverified gap: `STRICT` tables.** 18 of notare's tables are `STRICT`.
  cr-sqlite stores changeset values dynamically-typed and writes them back through
  the base table; if a type does not round-trip exactly, `STRICT` rejects the apply.
  Nothing upstream documents this and no test covers it. **Spike this before
  committing to a swap** — two in-process DBs, no transport, one sitting.
- **Maintenance risk:** upstream cr-sqlite's last tagged release is `v0.16.3`
  (2024-01-17) and its author's last commit is the same day; the five commits in the
  18 months since are drive-by build packaging by one external contributor. MIT means
  it can be forked and vendored, which is the point — but it would be an adopted
  dependency, not a maintained one. `superfly/cr-sqlite` (Fly.io, MIT, v0.17.0,
  active) is the maintained alternative, at the cost of breaking bookkeeping changes
  that push gap/seq tracking into the application.

`SYNCED_TABLES` is 8 of 17 registered tables. Every enabled table has a §17-style

`docs/internal/sync-p2p.md` §17, §19, §23, §25, §27.

| `session_documents` | ✅ | §17, plus the §19 FK correction |
| `transcripts` | ✅ | §23.3 — incl. a realistic ~800KB `words_json` row over a real sync round |
| `action_items` | ✅ | §23.3 — first proof to replay a post-creation `ALTER TABLE` (action_items_v2) |
| `tags` | ✅ | §23.4 — under the app's real deterministic-id write pattern |

⚠️ **Proofs do not run in CI.** Grepping `.github/workflows/` for the example names
returns nothing; CI only runs `cargo check -p cloudsync --features from-source` on
four platforms. All five proof examples (~2,555 LOC) are hand-run
`cargo run --features from-source` on linux/x86_64. There is no regression net —
getting at least the two-node schema proofs into CI belongs in 0.7's scope.

### Tables deliberately NOT enabled

Four are **proven unsafe**, not merely unproven — each duplicates the entity under
concurrent creation because the primary key is a locally-minted
`crypto.randomUUID()` while the real identity lives elsewhere. The `db-app` guard
test pins all four verdicts. **This analysis is about application id minting, not
the engine — it survives an engine swap unchanged.**

| Table | Status | Real identity | Evidence |
|---|---|---|---|
| `humans` | ⛔ do not enable | `lower(email)` | §25.2 — duplicates on both write paths |
| `session_participants` | ⛔ do not enable | `(session_id, human_id)` | §25.2 |
| `calendars` | ⛔ do not enable | `tracking_id_calendar` | §26.2 |
| `events` | ⛔ do not enable | `tracking_id_event` | §26.2 — worst case: the duplicating write is the poller, so it fires per device automatically |

Three are **unused** — no live app write path, so there is no write pattern to
model: `daily_notes` and `session_attachments` (only `legacy_import.rs`),
`entity_mentions` (nothing, anywhere). §28.

Two remain **unproven and unattempted**: `chat_groups`, `chat_messages`. §25.1.
(`feat/sync-table-proofs-b1` / PR #157 carries proofs for these plus batch 3–4
enables; **parked** pending §0.)

⛔ **GATE: BLOCK.** Nothing has ever *run* the sync stack off linux/x86_64.
`P2pAgent::start`, the C socket layer in `network_p2p.c` (Winsock2 vs POSIX), and a
real two-peer round trip are compile-and-link proven only. The Winsock2 port has
been *compiled* on Windows (§21.17) and never *executed* anywhere. Clearing this
needs either a real integration test in CI or manual verification on physical/VM
hardware.

⛔ **GATE: BLOCK — packaged-install verification.** #154 fixed two defects that made
installed builds unlaunchable (the from-source extension resolved a compile-time
`OUT_DIR` path that does not exist on a user's machine; and a failed extension load
panicked before tracing existed, killing the process silently). The fix is
compile-proven and regression-tested, and a `desktop_test_build` ran green — but
that proves the build, not the install.

**Note:** if the engine swaps, both blocks change shape rather than disappearing.
cr-sqlite has no custom C network layer, which removes the Winsock2-vs-POSIX risk
entirely, but it is still a loadable extension with the same packaged-install
resolution problem #154 fixed.

### Correction carried forward

`plugins/db/src/sync.rs:21` and the three-node proof describe an "elected-hub
topology". **There is no election in the code.** The app sets `connection_string:
agent.address()` (`sync.rs:88`) — every device points at its own broker. The hub is
a property of the proof harness (`sync_three_nodes.rs` hand-wires B and C to
allowlist only A), not of the app. Whether the app's self-pointing configuration is
intended or a gap is an open question for 0.7, independent of the engine.

## D. Non-goals carried from 0.6

Recorded so they read as decisions rather than omissions.

- **Hub failover / election** (§15.2, §20.10) — unbuilt. Note the app does not
  implement election at all today; see §B's correction.
- **Blob-log GC** (§15.2, §20.10) — the broker retains every blob forever. Moot if
  the engine swaps: cr-sqlite has no blob log.
- **The 9 remaining disabled tables** — 4 proven unsafe (fix named in §25.4/§26.3),
  3 unused, 2 unproven.
- **`strstr`-based JSON parsing** in `network_p2p.c` (§12, §21.4) — production
  hardening for a typed codec, never touched. Moot if the engine swaps.
- **No hostile-broker/peer test fixture** (§12) — nothing tests behaviour against a
  malicious or malformed peer.
- **Scheduled re-run of the `#[ignore]`d real-network discovery test** (§20.10).
- **`templates` fresh-device re-seed** (§27.4) — a device joining an existing sync
  set replays the default-template seed and resurrects built-ins deleted elsewhere.
  Nodes converge, so it is a seeder bug, not a CRDT one — but enabling `templates`
  is what makes it cross-device. Fix belongs in the seeder (seed once per database
  behind a marker). A reviewer may reasonably reverse the decision to enable
  `templates` because of this.

## Summary — what blocks 0.7 sync today

1. ⛔ **Engine undetermined** (§0) — the ELv2 denial. Gated on an unsent email, then
   on a decision. This is the one blocker that is not clearable by us alone.
2. ⛔ The sync stack has never been executed on macOS or Windows (§B).
3. ⛔ No packaged install verified since the #154 packaging fix (§B).
4. ⚠️ Convergence proofs are hand-run and outside CI (§A).

Order matters: **do not spend on 2, 3 or 4 until 1 resolves.** Every proof in §A is
evidence about sqlite-sync's `cls` semantics; if the engine changes, that work is
re-run, not reused.
